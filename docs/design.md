# Design: ระบบติดตามงานทีม

เอกสารออกแบบจาก `docs/plan.md` และ `docs/requirements.md` โดยถือสองไฟล์นั้นเป็นข้อกำหนดหลัก ไม่แก้ขอบเขตหรือเกณฑ์ยอมรับ เอกสารนี้เป็นแบบสำหรับพัฒนา ยังไม่ใช่โค้ดแอปหรือคำสั่งสร้างฐานข้อมูลที่รันแล้ว

## 1. ขอบเขตและแนวทาง

- งานหลัก: US-1 ถึง US-4 ตามลำดับ งานเสริม: US-5 และ US-6
- Next.js 16 App Router, TypeScript และ Tailwind สำหรับหน้าเว็บ; Supabase Auth สำหรับบัญชีและ session (สถานะการล็อกอิน); Postgres สำหรับข้อมูล; Vercel สำหรับเผยแพร่เว็บ
- ใช้ Supabase client แบบผูกกับผู้ใช้ ผ่าน publishable key เท่านั้น ทั้งใน browser และ server ไม่ใช้ secret key หรือสิทธิ์ผู้ดูแลเพื่อหลบการตรวจสิทธิ์
- เปิด RLS (กฎจำกัดแถวข้อมูลตามผู้ใช้) ทุกตารางใน `public` และใช้ constraint (ข้อบังคับข้อมูล), trigger (งานอัตโนมัติเมื่อข้อมูลเปลี่ยน) และ function ในฐานข้อมูลเสริมกติกาที่ RLS ตรวจเพียงอย่างเดียวไม่พอ
- ปิด Cache Components ตามโครงเว็บตั้งต้น ข้อมูลผู้ใช้และข้อมูลทีมไม่เก็บใน cache ที่ใช้ร่วมข้ามบัญชี
- ขั้นนี้เขียนเฉพาะ `docs/design.md` ใช้ `AGENTS.md` เดิมซึ่งมี stack, คำสั่ง และกติกาครบแล้ว

## 2. Data model (โครงสร้างข้อมูล)

ทุก `id` ที่สร้างเองใช้ `uuid` และ `gen_random_uuid()`; เวลาเหตุการณ์ใช้ `timestamptz default now()` ส่วนวันกำหนดส่งใช้ `date` ไม่มีเวลา

### 2.1 บัญชีและข้อมูลผู้ใช้ — US-1, AC-1.1–AC-1.4

`auth.users` เป็นตารางที่ Supabase Auth ดูแล เก็บอีเมลและข้อมูลยืนยันตัวตน ไม่สร้างตารางรหัสผ่านเองและไม่เปิดให้อ่านผ่านหน้าเว็บ

| ตาราง | คอลัมน์ | ชนิด | ข้อบังคับและหน้าที่ |
| --- | --- | --- | --- |
| profiles | id | uuid | PK (คีย์หลัก), FK (คีย์อ้างอิง) → `auth.users.id`, `on delete cascade` |
| profiles | display_name | text | NOT NULL, ชื่อหลังตัดช่องว่างยาว 1–100 ตัวอักษร |
| profiles | email | text | NOT NULL, สำเนาอีเมลจาก `auth.users.email` สำหรับข้อมูลสมาชิกและ US-6 |
| profiles | created_at | timestamptz | NOT NULL, default `now()` |

- เมื่อสมัครสำเร็จ trigger ที่ `auth.users` สร้าง profile ในธุรกรรมเดียวกัน โดยรับชื่อจาก metadata `display_name` และตรวจชื่อก่อนบันทึก อีเมลอ่านจาก Auth เท่านั้น ไม่รับจาก metadata
- หากสร้าง profile ไม่ได้ ให้การสมัครล้มเหลวพร้อมกัน ไม่ทิ้งบัญชีที่ไม่มี profile
- หากอีเมลใน Auth เปลี่ยน ให้ trigger ซิงก์ `profiles.email` ด้วย แม้ยังไม่มีหน้าจอแก้อีเมลในรอบนี้
- ผู้ใช้แก้ `email` หรือสวมรอย `id` ผ่านตาราง profiles ไม่ได้ ชื่อและอีเมลมองเห็นเฉพาะเจ้าตัวและเพื่อนร่วมทีมตามแผน ไม่มีหน้าแก้ profile ในขอบเขตนี้

### 2.2 ทีมและสมาชิก — US-2, AC-2.1–AC-2.6

| ตาราง | คอลัมน์ | ชนิด | ข้อบังคับและหน้าที่ |
| --- | --- | --- | --- |
| teams | id | uuid | PK |
| teams | name | text | NOT NULL, ชื่อหลังตัดช่องว่างยาว 1–100 ตัวอักษร |
| teams | invite_code | text | NOT NULL, UNIQUE, CHECK ตรงรูปแบบ `^[ABCDEFGHJKLMNPQRSTUVWXYZ23456789]{6}$` |
| teams | leader_id | uuid | NOT NULL, FK → `auth.users.id`, UNIQUE; หัวหน้าคือผู้สร้างทีม |
| teams | created_at | timestamptz | NOT NULL, default `now()` |
| team_members | user_id | uuid | PK, FK → `profiles.id`; PK นี้บังคับ 1 คนมีได้เพียง 1 ทีม |
| team_members | team_id | uuid | NOT NULL, FK → `teams.id` |
| team_members | joined_at | timestamptz | NOT NULL, default `now()` |

- เพิ่ม UNIQUE `(team_id, user_id)` ที่ team_members เพื่อใช้เป็นเป้าหมายของ FK แบบสองคอลัมน์
- เพิ่ม FK `(teams.id, teams.leader_id)` → `team_members(team_id, user_id)` แบบ `DEFERRABLE INITIALLY DEFERRED` (ตรวจเมื่อจบธุรกรรม) ทำให้หัวหน้าต้องเป็นสมาชิกทีมตัวเอง และสร้างทีมพร้อมสมาชิกหัวหน้าได้ในธุรกรรมเดียว
- ไม่เก็บบทบาทซ้ำใน team_members: ถ้า `user_id = teams.leader_id` แสดง “หัวหน้า” นอกนั้นแสดง “สมาชิก” จึงไม่มีบทบาทสองแห่งที่ขัดกันได้
- ชื่อทีมซ้ำกันได้ แต่รหัสเชิญซ้ำกันไม่ได้ สุ่มด้วยแหล่งสุ่มเชิงเข้ารหัสจากชุด `ABCDEFGHJKLMNPQRSTUVWXYZ23456789` และสุ่มใหม่เมื่อชน UNIQUE
- สร้างทีม/เข้าทีมผ่าน function เท่านั้น ไม่มีสิทธิ์เขียน team_members โดยตรง ไม่มีการออกทีม เปลี่ยนหัวหน้า เตะสมาชิก หรือแก้ทีมผ่านเว็บในรอบนี้

### 2.3 งาน — US-3 ถึง US-5

| ตาราง | คอลัมน์ | ชนิด | ข้อบังคับและหน้าที่ |
| --- | --- | --- | --- |
| tasks | id | uuid | PK |
| tasks | team_id | uuid | NOT NULL, FK → `teams.id` |
| tasks | title | text | NOT NULL, หลังตัดช่องว่างยาว 1–200 ตัวอักษร |
| tasks | description | text | NULL ได้, รายละเอียดไม่บังคับ |
| tasks | due_date | date | NULL ได้, วันกำหนดส่งตาม Asia/Bangkok |
| tasks | assignee_id | uuid | NOT NULL, FK → `profiles.id` |
| tasks | created_by | uuid | NOT NULL, FK → `auth.users.id`; ตรวจว่าคือหัวหน้าที่ล็อกอิน |
| tasks | status | text | NOT NULL, default `todo`, CHECK อยู่ใน `todo`, `in_progress`, `done` |
| tasks | created_at | timestamptz | NOT NULL, default `now()` |
| tasks | updated_at | timestamptz | NOT NULL, default `now()`; trigger ตั้งใหม่เมื่อแก้ข้อมูล |

- FK `(team_id, assignee_id)` → `team_members(team_id, user_id)` บังคับว่าผู้รับงานอยู่ทีมเดียวกับงาน แม้เรียกฐานข้อมูลตรง (AC-3.4)
- FK `(team_id, created_by)` → `team_members(team_id, user_id)` และ trigger ตรวจว่าผู้สร้างคือหัวหน้าทีมนั้น (AC-3.3)
- เพิ่ม index `team_members(team_id)`, `tasks(team_id, status)` และ `tasks(assignee_id, due_date)` รองรับรายการทีมและงานของฉัน
- ไม่ใช้ cascade เพื่อลบทีม สมาชิก หรืองานโดยอัตโนมัติ การลบข้อมูลที่ยังถูกอ้างอิงให้ถูกปฏิเสธจนผู้ดูแลจัดการข้อมูลที่เกี่ยวข้องอย่างตั้งใจ
- ไม่เก็บ `is_overdue` เพราะเปลี่ยนตามวัน คำนวณจาก `due_date < วันที่ปัจจุบันใน Asia/Bangkok` และ `status <> 'done'` เสมอ (AC-4.5)

## 3. ตารางสิทธิ์ — แบบสำหรับ RLS

SELECT = อ่าน, INSERT = เพิ่ม, UPDATE = แก้ไข, DELETE = ลบ; “–” หมายถึงไม่อนุญาตผ่าน API ของผู้ใช้ บทบาทหัวหน้า/สมาชิกคำนวณจากบัญชีที่ยืนยันตัวตนแล้ว ไม่รับบทบาทจากฟอร์ม

| ตาราง | บทบาท/แถวเป้าหมาย | SELECT | INSERT | UPDATE | DELETE |
| --- | --- | --- | --- | --- | --- |
| profiles | anon (ยังไม่ล็อกอิน) | – | – | – | – |
| profiles | เจ้าของแถว | ได้ | – | – | – |
| profiles | หัวหน้าหรือสมาชิก อ่านเพื่อนร่วมทีม | ได้ | – | – | – |
| profiles | คนนอกทีม อ่านผู้อื่น | – | – | – | – |
| teams | anon | – | – | – | – |
| teams | หัวหน้าทีมตนเอง | ได้ | ผ่าน `create_team` | – | – |
| teams | สมาชิกทีมตนเอง | ได้ รวมรหัสเชิญ | – | – | – |
| teams | ผู้ยังไม่มีทีมหรือคนนอกทีม | – | ผ่าน `create_team` เมื่อยังไม่มีทีม | – | – |
| team_members | anon | – | – | – | – |
| team_members | หัวหน้าหรือสมาชิก อ่านทีมตนเอง | ได้ | ผ่าน function เท่านั้น | – | – |
| team_members | ผู้ยังไม่มีทีมหรือคนนอกทีม | – | ผ่าน `create_team`/`join_team` สำหรับตนเองเมื่อยังไม่มีทีม | – | – |
| tasks | anon | – | – | – | – |
| tasks | หัวหน้า อ่าน/เขียนงานในทีมตนเอง | ได้ | ได้ | แก้ข้อมูลธุรกิจได้ | – |
| tasks | สมาชิกซึ่งเป็นผู้รับงาน | ได้ | – | เฉพาะสถานะ | – |
| tasks | สมาชิก อ่านงานที่มอบให้คนอื่น | ได้ | – | – | – |
| tasks | ผู้ยังไม่มีทีมหรือคนนอกทีม | – | – | – | – |

- เปิด RLS ทั้ง profiles, teams, team_members และ tasks พร้อมกำหนดสิทธิ์ตารางให้ตรงกับ matrix ไม่สร้าง policy สำหรับ anon
- profiles SELECT: `id = auth.uid()` หรือเจ้าของแถวนั้นอยู่ทีมเดียวกับผู้เรียก ห้ามเปิดอ่าน profiles ของทุกบัญชี
- teams/team_members/tasks SELECT: `team_id` ของแถว (หรือ `teams.id`) ต้องตรงกับทีมของผู้เรียก ป้องกัน AC-2.6 และ AC-3.7
- tasks INSERT: `WITH CHECK` ตรวจทีมของผู้เรียก, ผู้เรียกเป็นหัวหน้า, `created_by = auth.uid()` และสถานะเริ่มต้น `todo`
- tasks UPDATE: ใช้ทั้ง `USING` (แถวเดิม) และ `WITH CHECK` (แถวใหม่) ให้เฉพาะหัวหน้าหรือผู้รับงานในทีมตนเอง แล้วให้ trigger ตรวจการเปลี่ยนคอลัมน์เพิ่มเติม
- การสร้าง profile โดย Auth trigger และการเพิ่มทีม/สมาชิกโดย function เป็นช่องทางเฉพาะที่ตรวจสิทธิ์เอง ไม่ใช่การเปิด INSERT policy ให้ผู้ใช้เขียนตารางเหล่านี้ตรง ๆ
- การลบงานผ่าน Supabase Table Editor ตามแผนเป็นงานของผู้ดูแลที่เข้าหน้า Dashboard เท่านั้น ไม่เปิด DELETE ให้หัวหน้าผ่าน publishable key

## 4. Function และ trigger ที่ฐานข้อมูล

### 4.1 หลักการร่วม

- RPC (เรียก function ในฐานข้อมูลผ่าน API) รับเฉพาะข้อมูลที่จำเป็น ใช้ `auth.uid()` เป็นผู้กระทำ ไม่รับ `user_id`, `leader_id` หรือบทบาทจากผู้เรียก
- `create_team`, `join_team` และ helper สำหรับ RLS ใช้ `SECURITY DEFINER` (ทำงานด้วยสิทธิ์เจ้าของ function) เฉพาะเท่าที่จำเป็น เพื่ออ่านข้อมูลที่ผู้ใช้ยังไม่มีสิทธิ์อ่าน
- ตั้ง `search_path` ว่าง อ้างชื่อตารางพร้อม schema ทุกครั้ง ไม่ประกอบ SQL จากข้อความผู้ใช้ ใช้เจ้าของ function ที่เชื่อถือได้ และตรวจผู้เรียกก่อนคืนข้อมูล
- ถอน EXECUTE จาก `PUBLIC` และ `anon` แล้วให้ `authenticated` เฉพาะ RPC/helper ที่ต้องใช้ ส่วน trigger function ไม่เปิดให้ผู้ใช้เรียกโดยตรง
- RLS helper ต้องอ่านตารางเองโดยไม่ย้อนเข้าชุด policy เดิม ป้องกัน policy เรียกวนระหว่าง profiles, teams และ team_members

### 4.2 รายการ function

| ชื่อ | ข้อมูลรับเข้า | ขั้นตอนและผลลัพธ์ | เกณฑ์ที่รองรับ |
| --- | --- | --- | --- |
| `current_team_id()` | ไม่มี | คืนเฉพาะทีมของ `auth.uid()` หรือ NULL; anon ได้ NULL ไม่รับ id บุคคลอื่น | AC-2.6, AC-3.7 |
| `is_team_leader(target_team_id)` | id ทีม | คืน true เมื่อผู้เรียกเป็นสมาชิกและหัวหน้าทีมนั้น นอกนั้น false ไม่คืนชื่อทีมหรือข้อมูลสมาชิก | AC-3.3, AC-4.2 |
| `shares_team_with(target_user_id)` | id ผู้ใช้ | คืน true เมื่อทั้งคู่มีทีมเดียวกัน ไม่เปิดให้ค้นอีเมลหรือรายชื่อคนนอกทีม | AC-2.6 |
| `create_team(team_name)` | ชื่อทีม | ตรวจล็อกอิน, ล็อกแถว profile ของผู้เรียก, ตรวจว่ายังไม่มีทีม, ตรวจชื่อ, สุ่มรหัส แล้วเพิ่ม teams และ team_members พร้อมกัน คืน id ทีมตนเอง | AC-2.1, AC-2.2, AC-2.4, AC-2.5 |
| `join_team(invite_code)` | รหัสเชิญ | ตรวจล็อกอิน, ล็อก profile ของผู้เรียก, ตรวจว่ายังไม่มีทีม, trim/แปลงรหัสเป็นตัวพิมพ์ใหญ่, ค้นทีมด้วยรหัสตรงกัน แล้วเพิ่มสมาชิก คืน id ทีมหลังเข้าร่วมสำเร็จ | AC-2.3, AC-2.4, AC-2.6 |

- ทั้งสร้างและเข้าทีมล็อกแถว profile เดียวกัน (`FOR UPDATE`) และทำในธุรกรรมเดียว ร่วมกับ PK ของ team_members เพื่อไม่ให้คำขอพร้อมกันพาผู้ใช้เข้าหลายทีม หรือทิ้งทีมเปล่าเมื่อเพิ่มสมาชิกไม่ได้
- เมื่อพบว่ามีทีมแล้ว ทั้งสอง function คืนข้อผิดพลาดที่แปลงเป็น “คุณมีทีมอยู่แล้ว” แม้เรียกข้ามหน้าจอ; ตรวจกรณีนี้ก่อนค้นรหัสทีมอื่น
- `join_team` ไม่คืนรายละเอียดของทีมก่อนเพิ่มสมาชิกสำเร็จ รหัสผิดหรือรูปแบบไม่ถูกต้องใช้ข้อความเดียว “ไม่พบทีมจากรหัสนี้” ไม่เปิด endpoint ให้ค้นรหัสทั้งหมด
- ชื่อทีมว่างใช้ข้อความ “กรุณากรอกชื่อทีม” ไม่ปล่อยข้อความ SQL ภายในออกหน้าเว็บ

### 4.3 กติกาของ trigger งาน — AC-3.1, AC-3.3–AC-3.5, AC-4.1–AC-4.4

- INSERT: ตรวจบัญชีจาก `auth.uid()`, เป็นหัวหน้าทีมของงาน, ผู้สร้างตรงบัญชี และสถานะเป็น `todo`; FK ตรวจสมาชิกผู้รับงาน; ชื่องานว่างใช้ “กรุณากรอกชื่องาน”
- UPDATE: ห้ามเปลี่ยน `id`, `team_id`, `created_by`, `created_at` เพื่อป้องกันย้ายงานข้ามทีมหรือสวมรอยผู้สร้าง
- หัวหน้าแก้ `title`, `description`, `due_date`, `assignee_id`, `status` ได้ในระดับฐานข้อมูลตามแผน แต่รอบนี้ไม่มีหน้าแก้ไขหรือลบงาน ผู้รับใหม่ยังต้องผ่าน FK ของสมาชิกทีม
- ผู้รับงานซึ่งไม่ใช่หัวหน้าเปลี่ยนได้เฉพาะ `status` เปรียบเทียบค่า OLD/NEW ของทุกคอลัมน์อื่นด้วย `IS DISTINCT FROM` รวมค่า NULL และปฏิเสธหากต่างกัน ส่วน `updated_at` ให้ trigger ตั้งเอง ห้ามรับค่าที่ผู้ใช้พยายามแก้
- ผู้ที่ไม่ใช่หัวหน้าและไม่ใช่ผู้รับงานถูกปฏิเสธทั้งจาก RLS และการตรวจใน trigger
- สถานะเปลี่ยนไปมาระหว่างสามค่าที่กำหนดได้ ไม่บังคับว่าต้องเดินหน้าอย่างเดียว เพราะ AC-4.1 ให้เลือกได้ทั้งสามสถานะ

## 5. การยืนยันตัวตนและลำดับคำขอ

### US-1 — AC-1.1–AC-1.5

1. `/login` มีสมัครสมาชิกและล็อกอิน สมัครรับชื่อ อีเมล รหัสผ่านอย่างน้อย 6 ตัวอักษร ตรวจทั้งฟอร์มและฝั่ง server; ตั้งความยาวขั้นต่ำใน Supabase Auth ให้ตรงกัน
2. สมัครด้วย Supabase Auth พร้อม metadata ชื่อ ให้ Auth trigger สร้าง profile จากนั้นพาไป `/team` เมื่อตรวจพบ session แล้ว
3. Workshop ให้ผู้ใช้ปิด Confirm email ใน Dashboard ตามแผน เพื่อให้ AC-1.1 สมัครแล้วล็อกอินได้ทันที ก่อนใช้งานจริงต้องเปิดกลับและออกแบบการยืนยันอีเมลเพิ่มเติม
4. ล็อกอินผิดใช้ข้อความ “อีเมลหรือรหัสผ่านไม่ถูกต้อง” และอยู่ `/login`; แถบบนอ่านชื่อจาก profile ของผู้ใช้ ไม่เชื่อชื่อจากฟอร์มครั้งล่าสุด
5. ใช้ SSR cookie ของ Supabase และ `proxy.ts` รีเฟรช session; ตรวจผู้ใช้ฝั่ง server ด้วย `getUser()` หรือ `getClaims()` ทุกหน้าที่ป้องกันและทุก Server Action (งานที่ฟอร์มเรียกฝั่ง server)
6. cookie แบบคงอยู่และระยะเวลา session ใน Supabase ต้องรองรับปิด/เปิด browser ภายในวันเดียวกัน (AC-1.4) ทดสอบด้วย browser ที่อนุญาตเก็บ cookie และไม่ใช่โหมดลบข้อมูลเมื่อปิด
7. ออกจากระบบด้วย Auth signOut แล้วไป `/login` พร้อมรีเฟรชข้อมูลหน้าจอ ไม่แสดงข้อมูลทีมที่ค้างจากบัญชีก่อน

### US-2 ถึง US-5 — คำขอข้อมูลและการเขียน

- ตรวจผู้ใช้ก่อนเรียกฐานข้อมูลเสมอ ผู้ไม่ล็อกอินไป `/login` (AC-1.5)
- เรียก `create_team`/`join_team` แล้วอ่านข้อมูลทีมด้วย client ของผู้เรียก ไม่อ่าน teams แบบไม่กรองเพื่อหารหัสเชิญ
- เมื่อสร้างงาน อ่าน team และหัวหน้าจากฐานข้อมูล กำหนด `team_id`/`created_by` จากบัญชีผู้เรียก รายชื่อผู้รับดึงจากสมาชิกทีมเดียวกัน แล้ว INSERT ผ่าน RLS
- การแก้สถานะส่ง `task_id` และสถานะที่เลือก ตรวจค่าที่รับ แล้ว UPDATE เฉพาะ `status`; ไม่รับออบเจ็กต์งานทั้งก้อนมาอัปเดต
- เมื่อบันทึกสำเร็จ รีเฟรช `/tasks` และ `/my` ให้ตำแหน่งงานเปลี่ยนทันทีหลังบันทึก (AC-4.1, AC-5.4) ไม่ต้องเพิ่มระบบ realtime ในรอบนี้
- อัปเดตพร้อมกันยึดการบันทึกที่สำเร็จล่าสุดเป็นค่าปัจจุบัน เป็นสมมติฐานที่ปรับได้

| route | หน้าที่และสิ่งที่แสดง | การเข้าถึง | US / AC |

| `/login` | สมัคร/ล็อกอินด้วยอีเมล รหัสผ่าน และชื่อเมื่อสมัคร | ทุกคน; ผู้ล็อกอินแล้วไป `/team` | US-1, AC-1.1, AC-1.2 |

| `/tasks` | กระดานสามสถานะ; ชื่อ ผู้รับ และกำหนดส่ง; ฟอร์มสร้างเฉพาะหัวหน้า; ตัวเลือกเปลี่ยนสถานะตามสิทธิ์ | ต้องล็อกอินและมีทีม ไม่มีก็ไป `/team` | US-3, US-4, AC-3.1–AC-3.7, AC-4.1–AC-4.5 |
| `/my` | งานที่ `assignee_id = auth.uid()` ตัวเลือกแสดงงานเสร็จ และเปลี่ยนสถานะ | งานเสริม ต้องล็อกอินและมีทีม | US-5, AC-5.1–AC-5.4 และ AC-1.5 |

- `/tasks` เรียงคอลัมน์ `todo` = “ยังไม่เริ่ม”, `in_progress` = “กำลังทำ”, `done` = “เสร็จแล้ว” บนมือถือเรียงคอลัมน์ลงมา ไม่มีเลื่อนแนวนอนที่ความกว้าง 375px (NFR-4)
- วันที่แสดงแบบไทยด้วย locale `th-TH`; ค่า date เป็นวันปฏิทิน ไม่แปลงจนวันที่เลื่อนเพราะ UTC; วันปัจจุบันสำหรับป้ายเลยกำหนดใช้ Asia/Bangkok (AC-4.5)
- งานไม่มีกำหนดแสดง “ไม่มีกำหนด”; งานว่างทั้งทีมแสดง “ยังไม่มีงานในทีม” (AC-3.6)
- `/my` กรองเจ้าของงานเพิ่มจาก RLS เรียง `due_date ASC NULLS LAST` และ `created_at ASC` เมื่อวันเท่ากัน ซ่อน done เริ่มต้น; ไม่มีงานตามตัวกรองแสดง “ยังไม่มีงานที่ได้รับมอบหมาย” พร้อมลิงก์ `/tasks` (AC-5.1–AC-5.3)
- ทุกหน้าที่โหลดข้อมูลมีสถานะกำลังโหลด/ไม่มีข้อมูล/ผิดพลาดเป็นภาษาไทย ปุ่มบันทึกป้องกันกดซ้ำ แสดงข้อผิดพลาดติดกับฟอร์ม และใช้ label กับ input ที่อ่านได้ด้วยเครื่องมือช่วยอ่าน (NFR-3)

## 7. อีเมลแจ้งงาน — US-6 (งานเสริม)

1. เริ่มส่งจาก Server Action สร้างงานเท่านั้น หลัง INSERT สำเร็จและได้แถวงานกลับจากฐานข้อมูล ไม่เรียกส่งก่อนบันทึก (AC-6.2)
2. ตรวจผู้ใช้และหัวหน้าด้วย session ของคำขอนั้น อ่านผู้รับจาก `tasks.assignee_id → profiles.email` พร้อมชื่อทีมและชื่อผู้มอบหมายจากฐานข้อมูล ไม่รับอีเมลผู้รับ ชื่อทีม หรือชื่อผู้มอบหมายจาก payload มาใช้แทน (AC-6.4)
3. ส่ง Gmail SMTP ผ่านแพ็กเกจส่งอีเมลฝั่ง server เช่น Nodemailer ใช้ `GMAIL_USER` และ `GMAIL_APP_PASSWORD` ของบัญชีทดลองเท่านั้น เก็บใน `.env.local`/Vercel Environment Variables ไม่ใช้ prefix `NEXT_PUBLIC_` และไม่ส่งไป browser หรือ log (AC-6.5)
4. หัวเรื่อง `งานใหม่: <ชื่องาน>` เนื้อหามีชื่องาน วันกำหนดส่งหรือ “ไม่มีกำหนด” ชื่อทีม และชื่อผู้มอบหมาย ใช้ข้อความธรรมดาหรือ escape ข้อมูลก่อนประกอบ HTML (AC-6.1)
5. รอ SMTP ส่งจากคำขอเดียวกันทันทีหลังสร้าง ตั้ง timeout รวมไม่เกิน 20 วินาที ไม่ปล่อยงานเบื้องหลังที่อาจหยุดเมื่อ request ของ Vercel จบ และไม่เปิด API ให้ใครส่งอีเมลจาก task id ใดก็ได้
6. SMTP ล้มเหลวหรือ timeout ให้คงงานไว้และแสดง “สร้างงานแล้ว แต่ส่งอีเมลแจ้งไม่สำเร็จ” ไม่ rollback งาน และไม่ retry ด้วยการ INSERT งานใหม่ (AC-6.3)
7. AC-6.1 ต้องทดสอบกล่องจดหมายจริงว่าได้รับภายใน 1 นาทีในภาวะบริการปกติ การที่ SMTP รับข้อความยังไม่ใช่หลักฐานว่าถึงกล่องแล้ว เครือข่าย/ผู้ให้บริการอาจทำให้ช้า; ไม่อ้างว่า AC นี้ผ่านจาก unit test เพียงอย่างเดียว

## 8. ความปลอดภัยและการจัดการข้อผิดพลาด

- NFR-1: การเรียกตารางตรงด้วย publishable key ต้องผ่าน RLS เหมือนหน้าเว็บ; ห้ามแก้ปัญหาด้วยการเปิดอ่านทุกทีม
- NFR-2: `.env.local`, node_modules และ `.next` ไม่เข้า Git; ตัวอย่างเก็บเฉพาะชื่อตัวแปร/ค่าตัวอย่าง ไม่แสดงค่าคีย์จริงในเอกสารหรือข้อผิดพลาด
- validation ฝั่งหน้าเว็บช่วยให้กรอกง่าย แต่กติกาสิทธิ์และความถูกต้องต้องตรวจที่ฐานข้อมูลด้วย ป้องกันการข้ามฟอร์ม
- แปลงข้อผิดพลาดฐานข้อมูลเป็นข้อความไทย ไม่ส่ง stack trace หรือรายละเอียดที่เปิดเผยทีมอื่นกลับผู้ใช้ การเข้าถึงแถวที่ไม่มีสิทธิ์ใช้ข้อความกลางว่า “ไม่พบข้อมูลหรือไม่มีสิทธิ์”
- แนวทางเสริมก่อนใช้งานจริงนอก workshop: จำกัดความถี่การลองรหัสเชิญตามบัญชีที่ยืนยันตัวตนแล้ว โดยครอบคลุมการเรียก RPC ตรงด้วย การเพิ่มตัวนับ/ตารางต้องออกแบบ migration และ RLS เพิ่มก่อนทำ ไม่เพิ่มโครงสร้างนี้ใน US-1 ถึง US-6 ปัจจุบัน และไม่ถือว่าการจำกัดเฉพาะหน้าเว็บป้องกัน RPC ได้
- ไม่เพิ่มบัญชีผู้ดูแลในแอป ไม่เพิ่มการออกทีม/เปลี่ยนหัวหน้า/ลบงานผ่านเว็บตามขอบเขตเดิม

### บัญชีทดสอบตาม requirements

- A: หัวหน้าทีม 1; B: สมาชิกทีม 1; C: หัวหน้าทีม 2 ใช้ session แยกกัน
- ก่อน B เข้าทีม ให้ B ลองอ่าน teams/team_members/profiles ของ A ต้องไม่เห็น; หลังเข้าทีมจึงเห็นเพื่อนร่วมทีม C ยังคงไม่เห็น (AC-2.6)
- B สร้างงานไม่ได้; A มอบงานให้ C ไม่ได้; C อ่านงานทีม 1 ไม่ได้ ทั้งผ่านหน้าเว็บและ client ที่ใช้ publishable key ร่วมกับ session ของบัญชีนั้น (AC-3.3, AC-3.4, AC-3.7)
- B อัปเดตสถานะงานตัวเองได้ แต่แก้ชื่อ/รายละเอียด/กำหนดส่ง/ผู้รับไม่ได้ และแก้งานคนอื่นไม่ได้; A เปลี่ยนสถานะทุกงานทีมตนได้ (AC-4.1–AC-4.4)
- สร้างงานกำหนดเมื่อวาน วันนี้ พรุ่งนี้ และไม่มีกำหนด ตรวจป้ายข้ามเที่ยงคืนตามเวลาไทย รวมงานเสร็จที่ต้องไม่มีป้าย (AC-4.5)
- ทดสอบบัญชีที่ยังไม่ล็อกอินกับ `/team`, `/tasks`, `/my` และเรียกตารางตรง ต้องไม่มีข้อมูลส่วนบุคคล (AC-1.5, NFR-1)
- ตรวจข้อความไทย/สถานะโหลดและจอ 375px ทุกหน้าที่ทำแล้ว (NFR-3, NFR-4)

## 10. สมมติฐานที่ปรับได้และจุดตรวจสอบก่อนเริ่ม
